# 数据开发工作台：总体框架设计

> 这份文档回答"总体框架"：整个研发链路怎么被 Agent 承载，分几段、每段谁做、产出什么、界面出现什么卡片。用户面细节见 `docs/design/user-surface.md`。
> 产品形态见 `product-blueprint.md`，技术实现见 `workbench-harness.md`。
>
> **2026-10-25 · v2 蓝图**：目标阶段已收敛为 **需求 → 设计 → 方案 → 开发 → CICD → 复盘**。完整阶段/设计/组件矩阵见 [`blueprint-v2.md`](blueprint-v2.md)，可视化见 [`prototype/blueprint-v2.html`](../../prototype/blueprint-v2.html)。当前代码已按 6 段投影；下文 2.1 保留旧 7 段作为历史参考。

---

## 0. 框架是什么

**框架 = 阶段 × 产物 × 角色 × 能力 × 卡片。**

一句话原则：**阶段之间只传产物，不传对话。**

- 传对话：上下文越滚越大，第 5 段就忘了第 1 段；交接靠"你往上翻"。
- 传产物：每段有结构化输入输出，谁做的、做到哪、能不能进下一段，一目了然。

这就是你要的"总体框架"——它不是一张架构图，而是**一条有接口的流水线**。

## 1. 总体框架

```
                    ┌──────────────── 需求来源 ────────────────┐
                    │  devops：需求单 / 缺陷单 / 技术债          │
                    └──────────────────┬───────────────────────┘
                                       ▼
 ① 需求分析 ──► requirement.yaml ──► ② 数据设计 ──► design.yaml
   (BA)         目标/范围/验收              (架构师)    粒度/源→目标/加工逻辑/调度草案
                                       │
                                       ▼
 ③ 技术方案 ──► tech-plan.yaml ──► ④ 开发 ──► code/ + unit-test/
   (Tech Lead)   平台/任务/依赖/排期        (开发)      DDL / ETL SQL / 调度配置
                                       │
                                       ▼
 ⑤ 测试 ──► test-report.yaml ──► ⑥ 发布 ──► release.yaml ──► ⑦ 复盘
   (QA)         校验/回归/DQ              (发布)      变更单/CICD/回滚    知识沉淀

 贯穿：WorkItem（任务文件夹）· Evidence（证据）· Catalog/Lineage（事实）
 执行系统：建模平台 · ETL 平台 · 调度平台 · 变更系统 · CICD · 测试系统 · devops
```

**关键**：Agent 不替代任何执行系统，它在每段的**入口和出口**上工作——入口把材料备齐，出口把产物落盘并交给下一个系统。

## 3. 阶段产物：框架的接口

产物必须是**结构化文件**，不是聊天记录。原因：下一段的 Agent 要读它、UI 要渲染它、人要审它、系统要提交它。

### 3.1 产物清单

| 产物 | 必填字段（最小集） |
|---|---|
| `requirement.yaml` | 目标、范围、验收标准、影响资产、优先级、提出人 |
| `design.yaml` | 目标表、粒度、源表与字段、加工逻辑、分区、调度草案、口径 owner |
| `tech-plan.yaml` | 平台选型、任务拆分、依赖、SLA、工时、风险 |
| `test-report.yaml` | 校验项、阈值、实际值、结论、阻断项 |
| `release.yaml` | 变更单号、影响面、灰度策略、回滚方案、观察指标 |

### 3.2 `design.yaml` 长这样（最关键的一份）

```yaml
id: design-20261024-001
target:
  table: dws.trade_channel_daily
  grain: "渠道 × 日期"          # 必须一句话说清
  partition: dt
  layer: dws
sources:
  - table: dwd.orders
    fields: [order_id, channel_id, pay_time, amount]
    filter: "dt = ${bizdate}"
  - table: dim.channel
    join: channel_id
transform:
  - step: 过滤有效订单
    logic: "status in ('paid','shipped') and amount > 0"
  - step: 按渠道聚合
    logic: "count(distinct order_id), sum(amount)"
metrics:
  - name: order_cnt
    definition: 支付订单数（去重）
    owner: 交易组
schedule:
  cron: "0 3 * * *"
  depends_on: [dwd.orders@dt-1, dim.channel@dt]
  sla: "05:00 前产出"
acceptance:
  - "与旧口径差异 < 0.5%"
  - "空渠道占比 < 0.1%"
```

这一份文件同时是：架构师的产出、开发的任务书、测试的验收依据、调度配置的来源。
**它的字段设计，就是整个框架的核心设计。**

### 3.3 产物怎么传

- 落盘在 `workitems/<id>/artifacts/`，git 可 diff。
- 下一段 Agent 只读上游产物 + 调自己的工具，**不继承上一段的对话**。
- 人可以在任何一段直接改文件，Agent 下一轮读到的就是最新版。

## 4. Agent 花名册

| 角色 | 一句话职责 | 输入 | 输出 | 主要工具 | 明确不做 |
|---|---|---|---|---|---|
| **协调者** Coordinator | 路由、跟踪、催办、升级 | 需求单 | 分派 + 状态 | workitem、devops | 不写业务方案 |
| **需求分析师** BA | 把一句话需求变成可验收的规格 | devops 单、历史相似需求 | `requirement.yaml` | catalog、devops、指标库 | 不做技术选型 |
| **数据架构师** Architect | 把规格变成可执行的数据设计 | requirement、血缘、数据探查 | `design.yaml` | 血缘、profile、建模规范 | 不写最终代码 |
| **技术负责人** Tech Lead | 把设计映射到平台与任务 | design、平台能力目录 | `tech-plan.yaml` | 平台查询、成本估算 | 不替开发写 SQL |
| **数据开发** Engineer | 把方案写成可运行代码 | tech-plan、design | `code/`、单测 | 建模/ETL 平台、SQL 执行 | 不擅自改设计 |
| **测试** QA | 证明它按设计工作 | code、acceptance | `test-report.yaml` | 测试系统、校验 SQL | 不放宽阈值 |
| **发布** Release | 安全地送上线并可回滚 | test-report | `release.yaml` | 变更系统、CICD | 不跳过变更流程 |
| **知识管理员** Curator（可选） | 沉淀口径、模式、复盘 | 全部产物 | 知识条目、技能更新 | 文档、指标库 | 不改代码 |

**角色不是越多越好**。第一版可以只启用 3 个：协调者、架构师、开发；BA 和 Tech Lead 由协调者兼任，QA/Release 用技能+人工确认。

## 5. 卡片：为什么 DSH 的插件设计刚好对上

你的直觉是对的，而且 DSH 里已经有现成机制：

> `ui-tool` 把每个工具调用按**工具名**分发到 `tool.call.toolview` 这个 keyed slot；**没有注册视图的工具走通用卡片**。业务 UI 包只注册自己的工具名和视图，不需要重建会话。
> —— `packages/client/ui-tool/README.md`

翻译成产品语言：**平时就是普通对话（通用卡片），当某个阶段的能力被调用时，才出现那个阶段专属的卡片。** 这正是你说的"需要具体的能力才会有具体的卡片或者弹窗"。

### 5.1 三层渐进披露

| 层 | 什么时候出现 | 例子 |
|---|---|---|
| L0 通用 | 默认 | 一段回答、一次普通工具调用 |
| L1 阶段卡 | 该阶段工具被调用 / 产物生成 | 设计卡、方案卡、发布卡 |
| L2 全屏面板 | 人点"展开" | 设计画布、代码 diff、变更单预览 |

**卡片不是新东西，它是阶段产物的视图。** 产物是事实，卡片只是渲染方式——这样 UI 永远不会和真实状态脱节。

### 5.2 四张关键卡（线框）

**需求卡**

│ 目标：把渠道日报改成按支付口径            │

## 6. 四套方案

同样是"总体框架"，落到 Agent 组织上有四种做法，成本和体验差别很大。

### 方案 A：单 Agent + 阶段技能（Stage-as-Skill）

```
一个通用 Agent
  ├─ 技能：requirement / design / tech-plan / develop / test / release
  ├─ 卡片：每个阶段工具一个 toolview
  └─ 状态：workitems/ 文件夹
```

- **怎么工作**：一个 Agent 从头跟到尾，阶段靠技能切换，卡片靠工具触发。
- **优点**：最快（3 周可跑）；上下文连续，适合小需求；在 CC/OpenCode 也能跑。
- **缺点**：长需求上下文会膨胀；阶段纪律靠技能，容易跳步；没有角色隔离。
- **适合**：v1、单人、中小需求。

### 方案 B：协调者 + 角色 Agent（Agent Team）

```
Coordinator
  ├─ BA ──► requirement.yaml
  ├─ Architect ──► design.yaml
  ├─ Tech Lead ──► tech-plan.yaml
  ├─ Engineer ──► code/
  └─ QA / Release ──► test-report / release
```

- **怎么工作**：协调者分派，每个角色只拿到上游产物 + 自己的工具；交接靠文件。
- **优点**：上下文干净；权限可隔离（测试不能改代码）；和你们团队角色对应。
- **缺点**：交接协议没设计好会互相甩锅；调试链路长；协调者容易成为瓶颈。
- **适合**：中大型需求、多人协作（第二阶段）。

### 方案 C：阶段工作台（Stage-as-Workspace）

```
左侧阶段导航：需求 | 设计 | 方案 | 开发 | 测试 | 发布
每个阶段一个独立面板 + 内嵌 Agent
```

- **怎么工作**：不再是"一个对话走到底"，而是每个阶段有自己的工作区（设计画布、任务看板、代码工作台、测试报告）。
- **优点**：最像"平台"；阶段门禁可以在 UI 上强制；非技术角色也能用。
- **缺点**：最重（4 个月+）；容易做成 IDE；每块面板都要维护。
- **适合**：产品成熟后、有专门前端投入时。

### 方案 D：流程驱动（Stage-as-Pipeline）

```
devops/变更系统 驱动状态机
  └─ 每个阶段：headless 调用 Agent → 写回产物 → 人工门禁 → 下一段
```

- **怎么工作**：Agent 不在前台常驻，而是被流程系统按阶段调用（SDK / headless profile）。
- **优点**：和现有治理体系最贴合；可批量、可审计；不需要新 UI。
- **缺点**：没有交互式探索；强依赖工单系统 API；出问题难调。
- **适合**：标准化需求、批量改造、后台自动化。

### 对比

| 维度 | A 单 Agent | B 角色团队 | C 阶段工作台 | D 流程驱动 |
|---|---|---|---|---|
| Agent 数量 | 1 | 1 + 3~6 | 每阶段 1 | 每阶段临时 |
| 编排 | 技能 | 协调者 + 子代理 | 阶段状态机 | 外部流程 |
| UI 成本 | 低（卡片） | 低（卡片） | 高（面板） | 无 |
| 上下文质量 | 中 | 高 | 高 | 高 |
| 探索能力 | 高 | 中 | 高 | 低 |
| 与现有系统集成 | 中 | 中 | 中 | 高 |
| 工期 | 3 周 | 8 周 | 4 个月 | 6 周+ |
| 风险 | 上下文膨胀 | 交接协议 | 做成 IDE | 工单系统耦合 |

### 推荐：A 打底，B 增强，C 只做卡片，D 做后台

1. **框架先行（A）**：先把 7 段产物 schema 和 6 张卡片做出来——这是所有方案的公共底座。
2. **设计与技术方案两段升级为 B**：这两段最吃上下文、最需要"角色视角"（架构师 vs 技术负责人）。
3. **开发/测试/发布用 A 的卡片**：不做全屏工作台，成本不值。
4. **批量/标准化需求走 D**：作为后台能力，不占前台。

## 7. 和现有系统的集成点

| 系统 | 在框架里的角色 | 集成方式 | 阶段 |
|---|---|---|---|
| devops | 需求/缺陷来源、状态回写 | webhook / 轮询 / 手动粘贴 | ①⑦ |
| 元数据 + 血缘 | 事实来源 | MCP / API | ①②③ |
| 建模平台 | 建表、模型管理 | API / CLI | ③④ |
| ETL 平台 | 加工作业 | API / CLI | ③④ |
| 调度平台 | 调度配置、依赖、状态 | API | ③④⑥ |
| 测试系统 | 用例、校验结果 | API | ⑤ |
| 变更系统 | 变更单、审批 | API | ⑥ |
| CICD | 构建、部署、回滚 | API / webhook | ⑥ |
| 数据消费平台 | API/报表发布 | 后期 | ⑥ |

**接入顺序建议**：元数据/血缘 → 变更系统 → 调度 → 建模/ETL → 测试/CICD。先接"读"，再接"写"；先接"能验证价值"的，再接"提效最多"的。
