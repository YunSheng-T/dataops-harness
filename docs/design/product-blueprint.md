# 数据开发工作台：产品蓝图 v0.1

> 这份文档只回答产品问题：**谁用、用来干什么、长什么样、第一版做什么**。
> 总体框架（阶段/角色/方案）见 `docs/design/framework.md`；用户面见 `docs/design/user-surface.md`；技术实现见 `docs/design/workbench-harness.md`。

---

## 1. 一句话

**把"改表、排障、取数"这类数据开发任务，从"翻五个系统 + 拼 SQL"，变成"交代一件事 + 看结论 + 点提交"。**

它不是：
- ❌ 不是又一个 SQL 编辑器（编辑器你们有了）
- ❌ 不是替换 devops / 变更 / CICD（它们是执行系统，这个不碰执行）
- ❌ 不是"接了一堆 MCP 的聊天框"（那是你们已经验证过的东西）

它是：**变更与排障的"起草 + 论证 + 落单"层**。人负责决定，agent 负责把材料备齐，最后交给现有系统去执行。

---

## 2. 三个真实场景

### 场景 A：改一张表

> **你**：把 `dwd.orders` 的 `user_id` 改成 bigint，评估下影响，准备变更单。
>
> **工作台**（不是一段话，是一边查一边铺开）：
> - 查血缘 → 右侧出现 3 个下游：2 个任务、1 个 API
> - 查数据 → "近 7 天有 0.3% 为空，改类型前建议先清理"（可点开证据）
> - 起草 → 中间出现 `change.sql`：`ALTER TABLE …`
> - 起草 → 同时给出回滚语句和 2 条验证 SQL
> - 生成 → 变更单草稿：标题、影响面、变更内容、回滚方案、验证结果
>
> **你**：翻一眼影响清单，确认那个 API 的负责人知道这事，点【创建变更单】。
>
> **然后**：变更系统走它自己的流程，CICD 跑它的流水线。工作台只在旁边记录状态，不插手。

### 场景 B：任务失败

> **你**：把告警里的任务名贴进来。
>
> **工作台**：
> - 拉 run 信息、日志、上下游、最近变更
> - 给时间线："02:10 上游产出延迟 → 02:40 本任务超时 → 03:00 被 kill"
> - 给根因假设 + 证据（上游行数对比、日志关键行）
> - 给止血建议："先重跑 02:40 这批，上游补数后 04:10 再跑一次"
>
> **你**：确认后让它生成重跑单 / 修复 SQL。
>
> **关键**：它不会自作主张重启任务——因为重启是写操作，属于你们的调度系统。

### 场景 C：取数

> **你**：看看过去 7 天各渠道的下单转化，按天。
>
> **工作台**：
> - 找到 `dws.trade_channel_daily`，给一张"表卡"（粒度、分区、行数、口径）
> - 写 SQL、只读执行、给结果表
> - 标注："口径来自指标 `order_cvr_v2`，2026-09 改过一次"
>
> **你**：追问一句，或者把结果存成 artifact 发给同事。

**三个场景的共同点**：交代 → agent 铺开材料 → 你看结论 → 决定 → 交给现有系统。区别只是材料不同。

## 3. 产品长什么样

### 3.1 主界面：三栏

```
┌─────────────┬──────────────────────────────────┬─────────────────────┐
│ 任务          │  对话 / 产出                       │  上下文与证据         │
│             │                                  │                     │
│ ● 改 user_id │  你：把 user_id 改成 bigint…       │  📋 dwd.orders       │
│ ○ 排障 3821  │                                  │  200 万行/天 · dt 分区│
│ ○ 渠道转化    │  agent：先查了血缘，3 个下游        │                     │
│             │  ┌────────────────────────────┐  │  👥 下游 3 个         │
│ + 新建任务    │  │ 影响清单                    │  │   ├ dws.trade_daily  │
│             │  │ 1. dws.trade_daily（任务）   │  │   ├ ads.channel_rpt  │
│             │  │ 2. api.order_query（API）    │  │   └ api.order_query  │
│             │  │ 3. rpt.funnel（报表）        │  │                     │
│             │  └────────────────────────────┘  │  🧾 证据 5 条         │
│             │  ┌────────────────────────────┐  │   ▸ 空值率 0.3%      │
│             │  │ change.sql                  │  │   ▸ 下游任务最近调用   │
│             │  │ ALTER TABLE dwd.orders …    │  │   ▸ 字段类型分布      │
│             │  └────────────────────────────┘  │                     │
│             │                                  │  [在编辑器打开]       │
│             │  [提交到变更系统]  [导出]           │                     │
└─────────────┴──────────────────────────────────┴─────────────────────┘
```

- **左**：任务列表。一次任务 = 一个"文件袋"，关掉再打开还在。
- **中**：对话 + 产出。产出是文件（SQL / 报告 / 清单），不是聊天气泡。
- **右**：上下文。表卡、血缘、证据。**这一栏是工作台和聊天框最大的差别。**

### 3.2 证据卡片（点开长这样）

agent 说"近 7 天有 0.3% 为空"后面有个 `[证据 3]`，点开：

```
┌──────────────────────────────────────────────┐
│ 证据 #3                                       │
│                                              │
│ 结论：user_id 近 7 天有 0.3% 为 NULL           │
│ 查询：SELECT count(*) … WHERE dt BETWEEN …    │
│ 时间范围：2026-10-17 ~ 2026-10-24              │
│ 环境：prod 只读                                │
│ 查询时间：2026-10-24 17:30                     │
│ 结果：100 万行，3000 行为空                     │
│                                              │
│ [复制 SQL]  [在编辑器打开]  [重新执行]           │
└──────────────────────────────────────────────┘
```

**作用只有一个**：让 agent 说的每个数字都能被复核。没有它，结论就是黑盒。

### 3.3 提交前确认（对接变更系统）

```
┌────────────────────────────────────────────────┐
│ 创建变更单（草稿）                                │
│                                                │
│ 标题：dwd.orders.user_id 类型变更 → bigint       │
│ 影响：3 个下游（1 个 API，2 个任务）              │
│ 变更：ALTER TABLE dwd.orders MODIFY …           │
│ 回滚：ALTER TABLE dwd.orders MODIFY …           │
│ 验证：2 条 SQL（已附结果）                        │
│ 风险：0.3% 空值需先清理                          │
│                                                │
│ [取消]                        [创建变更单]       │
└────────────────────────────────────────────────┘
```

**注意**：这里只创建草稿，不直接执行。执行、审批、发布仍然在你们现有的变更 / CICD 系统里。第一版甚至可以不自动创建，只把内容填好让人复制过去。

## 4. 四个概念（大白话）

| 概念 | 大白话 | 类比 |
|---|---|---|
| **工作项 WorkItem** | 一次任务的全部材料，放在一个文件夹里 | 案卷 |
| **产出 Artifact** | 能直接用的东西：SQL、评审报告、影响清单 | 案卷里的正式文件 |
| **证据 Evidence** | 结论背后的那次查询（时间、环境、结果） | 卷宗里的笔录 |
| **表卡 Schema Card** | 一张表的关键信息卡：粒度、分区、行数、owner、关键字段 | 名片 |

这些不需要用户理解——用户只看到"任务、结论、证据、提交"。

## 5. 和现有系统的分工

```
开发者
  │ 交代任务
  ▼
┌─────────────────────────────┐
│  数据开发工作台               │  ← 本产品：起草、查证、铺材料
│  （读：catalog/血缘/SQL）     │
│  （写：本地文件 + 系统草稿）   │
└──────────┬──────────────────┘
           │ 变更单草稿 / 重跑单 / SQL
           ▼
┌──────────────┐   ┌──────────┐   ┌──────────┐
│  变更系统      │──►│  CICD    │──►│  devops  │
│（审批/发布）    │   │（构建/部署）│   │（运行态） │
└──────────────┘   └──────────┘   └──────────┘
           │
           └──► 状态回读（已提交/已审批/已发布）
```

**边界一句话**：工作台只写到"草稿"，不越过执行系统。这样既不用重做审批流，也不会和现有治理体系打架。

## 6. 第一版做什么（MVP）

| 做 | 不做 |
|---|---|
| 单用户、单任务 | 多人协作、评论、@人 |
| 读：表/任务/API 搜索、血缘、表卡 | 写平台（建表、改配置、触发任务） |
| 读：只读 SQL 执行（有行数/超时上限） | 批量巡检、定时任务 |
| 产出：SQL 文件、评审报告、影响清单 | 自动创建变更单（先只生成内容） |
| 证据卡片（点开能复核） | 审批流、电子签 |
| 任务文件夹（关掉再打开还在） | 移动端、桌面客户端 |

**MVP 的验收标准**：让一个数据开发用它完成一次真实的改表，从"开始"到"拿到可以提给变更系统的材料"，**不超过 20 分钟**，且材料能被另一个人直接看懂。

## 7. 分期

| 版本 | 内容 | 判断是否继续 |
|---|---|---|
| **v0.1（4 周）** | 三栏工作区 + 读能力 + 产物 + 证据 + 手动提交 | 3 个真实任务跑通，开发者愿意再用 |
| **v0.2（4 周）** | 对接变更系统（自动建草稿）+ 回读状态 + 排障场景 | 变更材料准备时间下降 50% |
| **v0.3（4 周）** | 写路径（经变更系统审批后执行）+ 重跑单 | 无一次越权操作 |
| **v1.0** | 批量巡检、团队视图、指标口径库 | 周活 ≥ 20 人 |

## 8. 怎么判断这东西有用

不看"对话轮数"，看四个数：

1. **一次改表的材料准备时间**：目标从 ~2 小时降到 20 分钟。
2. **材料齐全率**：影响面 / 回滚 / 验证 SQL 三项齐全的比例，目标 100%。
3. **返工率**：提给变更系统后被退回的比例，目标下降一半。
4. **复用率**：第二周还在用的人 / 第一周用过的人，目标 > 60%。

## 9. 下一步（三件事）

1. **陪跑一次真实变更**：找一位开发，他正常做，你在旁边记录他翻了哪些系统、查了什么、写了什么。这份记录比任何设计都准。
2. **定三栏线框**：把 3.1 的草图变成可点的原型（不用写代码）。
3. **定第一个对接系统**：建议先接**变更系统**（只创建草稿），因为它最能体现"省时间"，且不碰执行。
