## ctx.fs / FsVersion / replaceIfVersion

- `FsVersion` 是 branded opaque：`packages/fs/fs/src/types.ts:35`（`export type FsVersion = Branded<'FsVersion'>`），注释明确「consumers MUST NOT interpret this token」。
- `FsWriteIntent`：`types.ts:123-125` — `{ kind: 'createIfAbsent' } | { kind: 'replaceIfVersion'; version: FsVersion }`。
- 真实 outcome：`types.ts:128-144` — `FsWriteOutcome { operation: 'create'|'update'; version: FsVersion; before: string|null; after: string }`，**新 version 由真实写入产生**，满足「不得制造版本」。
- 错误码：`types.ts:175-188` — 含 `FS_STALE_VERSION`、`FS_NOT_OBSERVED`、`FS_TOO_LARGE`、`FS_NOT_REGULAR_FILE`、`FS_NOT_TEXT`、`FS_PERMISSION_DENIED`、`FS_SANDBOX_DENIED` 等，`FsError` 扩展 `HarnessError` 携带稳定 code。
- `writeText` 真实签名：`packages/fs/fs/src/index.ts:266-272` — `writeText(target, content, expected?: FsWriteIntent, signal?: AbortSignal, sandboxPolicy?: SandboxExecutionPolicy): Promise<FsWriteOutcome>`，与交接包设想的调用形完全一致。
- 其余证据：`stat` `index.ts:181`、`lstat`（不跟随末端符号链接）`index.ts:197`、`readText` `index.ts:205`、`readBytes`（带 maxBytes 上限，超限 `FS_TOO_LARGE` 不截断）`index.ts:228`、`watch` `index.ts:100`。

## fs-observation-policy 与 write/edit intent 组合

- 策略实现：`packages/fs/fs-observation-policy/src/index.ts` — `ObservedStateGate`（:21）以 `WeakMap<owner, Map<targetKey, FsObservation>>` 记录观察；`writeIntent`（:65-71）：未见/确认缺席 ⇒ `createIfAbsent`，确认存在 ⇒ `replaceIfVersion(观察版本)`；`editIntent`（:78-88）：未观察抛 `FS_NOT_OBSERVED`。
- actor/owner 语义：`src/types.ts:23-29` — owner 取自不透明 actor 的 `agent?.session`，作为 WeakMap 键，不读任何字段；无 agent 的调用「读自由，但写/编辑无法满足先观察策略」（:33-34 注释）。
- **关键组合事实**：该插件的三个监听器**从不调用 `next()`**（`src/index.ts:116-127` 注释：「occupy the single decision slot — do NOT call next()」）。
- waterfall 语义：`vendor/cordis/src/events.ts:225-243` — 监听器「outermost-first」，不调 `next()` 即否决链上其余监听器；注册顺序决定外层先后，默认 `push`（后注册者在内层），`ctx.on(name, fn, { prepend: true })` 可插到最外层（`events.ts:112-118` `EventOptions.prepend`，`:245-258` 注册实现）。
- 写路径消费点：`packages/fs/tool-fs/src/write.ts:121` — `ctx.waterfall('fs/write-intent', target, exec, () => undefined)`；随后 `ctx.fs.writeText(target, content, intent, exec.signal, sandboxPolicy)`（:125）。
- 装配点：`packages/bundle/base/cordis.patch.yml:292-293` — `fs-observation-policy` 在 base bundle 中、`tool-fs`（:295-296）之前。
- **对交接包「preset 显式保证组合顺序」的修正**：patch 文件头注释明确「Row order carries no load semantics (activation is service-availability driven)」（`cordis.patch.yml:12`）。真正的组合手段是**监听器注册顺序 + `prepend`**：dataops-dev bridge 必须以 `prepend: true` 注册在 observation policy 之外层，对 Agent/其他 actor 调 `next()` 落入原生策略，对认证 UI actor 自行返回受限 intent。这一机制比交接包假设更明确，P0 的 AGT-05（顺序错误安全失败）应翻译为「bridge 未 prepend 时 UI 保存失败而非静默降级」的合同测试。

## Remote 认证 / principal

- Remote 声明：`packages/api/workspace-files/src/index.ts:182-184` — `class WorkspaceFiles extends TypertRemoteService`，`static inject = ['fs','sandboxPolicy','sessions','typert']`；`@Remote` 装饰方法（:226 起）。
- Session 绑定：`src/index.ts:202-219` — 经 `typert.lookups.register('workspaceFileScope', ...)` 把线上 SessionId 解析为 Host 侧 scope（live header 或持久层 stat），**Client 不能任意伪造 Session 身份**；lookup 解析失败即 `gateway/lookup-not-found`。
- 错误体系：`RemoteError` 来自 `@deepseek-ai/dsh-typert-protocol`（如 `'workspace-file/not-text'`，`src/index.ts:248`），交接包的 `dev/*` 错误码可按同模式落地。
- 方法级访问控制：`packages/api/remote-access/README.zh.md:27-42` — Gateway 在解析 lookup、解码参数之前询问 `remoteAccess.decide({ principal, action, resources, args? })`；owner（`{ kind: 'owner' }`）不受检查，非 owner principal 按 role/binding/condition 判定；拒绝抛 `remote-access/denied`。
- 插件自带 Remote 的发布形态：`packages/experimental/api-speech-to-text/package.json` — exports 声明 `./typert`（`lib/typert.host.*`）与 `./remote`（`lib/typert.remote-client.*`）；生成器为已发布包 `@deepseek-ai/dsh-typert-generator@0.2.1-rc.4`，用法见 `packages/typert/generator/README.zh.md:28-47`（package.json 声明导出 → 构建生成 `lib/` 产物 → loader 注册贡献）；仓库级参考脚本 `scripts/generate-typert.ts`。
- **含义**：dataops-dev 的 DevDocument Remote 可在本仓 `packages/dataops-dev` 内声明 `@Remote` 方法并用 typert generator 产出 `./typert` / `./remote` 产物，不需改上游；这是我仓现有六个包还没用过的**新构建步骤**，需自建 build 脚本接入。
