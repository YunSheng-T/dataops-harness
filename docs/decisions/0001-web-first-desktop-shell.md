# ADR 0001：Web 首发，桌面壳作为同一 UI 的第二入口

- 状态：提议（待评审）
- 日期：2026-10-24
- 决策者：dataops-harness 项目组
- 相关：`docs/dataops-harness-blueprint.md`

## 背景

团队对分发形态有分歧：开发同学希望有一个"能当 IDE 用"的客户端，管理层倾向 Web。两边都不是无理要求：

- 开发同学的痛点是**上下文切换**：SQL、任务日志、血缘、报表配置分散在多个内部系统，希望在一个窗口里边聊边改边看结果。
- 管理层的诉求是**交付与运维成本**：Web 好发版、好灰度、好做权限与审计，不需要每个数据同学装客户端。

问题是：这两件事在 DSH 的架构里**不是互斥选项**。先把事实摆清楚。

## 事实（有据可查）

1. **DSH 只有一套 UI，就是 Web 客户端。** 桌面不是另一套前端：`dsh` 启动 Host，Host 通过 HTTP/WebSocket 提供页面；Electron 只是创建一个 BrowserWindow 去加载 `http://127.0.0.1:<port>`，并且明确"没有另造一条 renderer IPC 插件系统"（`dsh-desktop/docs/architecture.md` 启动顺序 5–6）。
2. **dsh-desktop 的工作量不在 UI 上。** 它的代码集中在窗口/托盘/单实例生命周期、profile 与内置 pnpm、终端、崩溃恢复、自动更新、双通道打包与签名。UI 部分只加了一条 36px 的 Desktop frame，兼容模式下官方 layout 原样运行（`docs/why-desktop.md`、`docs/architecture.md`）。
3. **"借现成 IDE 壳"这条路被上游关掉了。** ACP 曾是编辑器桥，上游已明确降级为 automation-only，并删掉了编辑器卡片、会话导航、模型/权限选择等呈现层（`.agents/notes/implemented/simplification/2026-07-23-acp-automation-only-protocol.md`）。想接 Zed/VS Code，得自己写客户端，不能指望上游。
4. **Web 客户端有真正的扩展点。** 第三方 client 插件可以通过 `ui-slots`（single/list/keyed/chain 四类 slot）、`ui-sidebar-right`（右侧标签页类型）、conversation node 定义加入界面（`packages/client/README.md`、`docs/subsystems/web-client.md`）。但 docking 引擎 `ui-dockkit` 被标注为 **Internal engine，随时可能变**——大面积自建 IDE 布局会踩在上游不承诺的 API 上。
5. **数据面可以完全独立于 UI。** 工具、技能、preset 都在 Host 侧，Web、桌面、SDK 三种入口共用同一套（`packages/sdk`、`apps/cli`）。UI 换壳不影响领域能力。

## 选项

| 方案 | 做法 | 成本 | 体验 | 主要风险 |
|---|---|---|---|---|
| **A. 纯 Web** | `dsh --profile dataops web`，内网部署 | 最低 | 浏览器里的对话 + 面板 | 本地文件/终端能力弱；重度用户嫌"不像工具" |
| **B. Web 首发 + 桌面壳**（推荐） | 同一套 UI；Electron 壳负责本地文件、终端、托盘、离线运行时 | 中（壳的生命周期是主要成本） | 开发同学拿到接近原生的窗口 | 打包/签名/更新；需要维护第二个分发物 |
| **C. Web + 客户端内自建 IDE 工作台** | 在 Web 客户端里用 slot + 右侧标签页做 SQL 编辑器/结果表/血缘图 | 中高 | 一体化最强 | `ui-dockkit` 是内部引擎；前端复杂度上升 |
| **D. 自有 IDE 前端 + SDK 后端** | VS Code 插件或自研 IDE，通过 SDK/自建协议调 harness | 高 | 最自由 | 两套产品；上游 ACP 不提供编辑器呈现层，全部自己写 |

## 决策

**采用 B，按阶段推进；C 只做高频面，不做全量 IDE。**

1. **第一版只发 Web（A 的能力，B 的骨架）。** 用 `dsh web` + 内网反向代理 + SSO 前置。这一版验证"数据同学愿不愿意用 agent 干活"，而不是"UI 像不像 IDE"。
2. **桌面壳作为增量，不阻塞 Web。** 当且仅当出现以下信号才启动：用户抱怨"每次都要开浏览器/传文件很麻烦"、需要本地目录/终端/离线、或需要托盘常驻。壳直接复用同一套 Web 构建产物，参照 dsh-desktop 的启动顺序，**不重写任何界面**。
3. **IDE 体验用三个渐进手段，而不是一次性造 IDE**：
   - ① 右侧面板插件：SQL 编辑器（Monaco）+ 结果表 + 血缘图，作为 `ui-sidebar-right` 的 tab 类型，Web 和桌面都能用（成本最低、收益最直接）。
   - ② 桌面壳带来本地能力：工作区目录、本地终端、拖拽文件。
   - ③ 只有当 ①② 被证明不够（例如用户要求多文件工程、Git 集成、调试器），才评估 D。
4. **不碰 `ui-dockkit` 的布局引擎。** 需要多面板时用右侧标签页 + 现有 `ui-layout` slot；把拖拽分屏留到上游稳定后再做。

## 为什么不是 A 或 D

- 不选 A：Web 能满足管理层，但满足不了开发同学的"工具感"，而工具感正是留存的关键。B 是在 A 之上加壳，边际成本远低于重做。
- 不选 D：等于同时维护两个产品，而且上游明确不提供编辑器侧呈现层，所有交互协议都要自己定义和演进。在领域价值还没验证前做这个，是把风险放在了错误的位置。

## 验收标准

| 阶段 | 指标 |
|---|---|
| Web v1 | 20 名数据开发试用 2 周；每周 ≥ 3 次真实任务（取数/改表/排障）；任务完成率 ≥ 70% |
| 右侧面板 | SQL 面板使用率 ≥ 40%；"复制到编辑器"行为下降 50% |
| 桌面壳 | 安装用户 ≥ 30%；崩溃率 < 0.5%；启动到可交互 < 5s |
| 是否做 D | 仅当 ≥ 30% 用户明确要求多文件工程/调试器，且 ①② 已上线 3 个月 |

## 后果

- 正面：一次 UI 投入，两种分发；领域能力（工具/技能/preset）与 UI 解耦；领导要的 Web 和开发要的客户端都能给。
- 负面：桌面壳的生命周期（签名、公证、自动更新、双平台）是长期负担；右侧面板会用到部分非稳定 API，需要锁版本 + 升级演练。
- 需要提前准备：内网部署的鉴权方案（DSH 本身不做 SSO）、桌面分发的代码签名证书、以及"Web 与桌面共用同一 profile 目录"的约定（dsh-desktop 用独立 app id 与独立 home 目录隔离，见其 `docs/architecture.md` 发行通道协议）。

## 一句话版本

> 先做 Web 把领域价值跑通；桌面壳复用同一套 UI，只在需要本地能力时加；IDE 体验从"右侧 SQL 面板"开始，不一次性造 IDE。
