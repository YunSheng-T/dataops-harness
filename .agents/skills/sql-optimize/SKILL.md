# SQL 优化

## 何时用

- 查询超时、被限流、或占用过多队列资源
- 扫描量/读取字节数明显高于预期
- 同样的 SQL 昨天能跑、今天跑不动
- 有人问「这条能不能快一点」

不适用：SQL 还没跑通过（先让它正确，再谈快）；或问题在调度/资源排队而非 SQL 本身。

## 先取事实

1. **基线**：当前耗时、扫描字节、峰值内存/并发、执行时间点
2. **计划**：`EXPLAIN` / `EXPLAIN ANALYZE` 输出（优先要真实的，不要猜）
3. **统计信息**：表行数、分区数、最近是否更新过统计
4. **数据特征**：是否有热点键、倾斜、空值比例
5. **约束**：能不能改 SQL、能不能加索引/物化、能不能改表结构

## 流程

1. **复现基线**：记录当前耗时与扫描量，作为对比基准。没有基线不做优化。
2. **读计划找瓶颈**：按代价排序——全表扫 → 大表 join 无过滤 → shuffle/重分布 → 数据倾斜 → 重复计算。
3. **提出候选**（一次只改一个变量）：
   - 分区裁剪 / 谓词下推
   - join 顺序与 broadcast 阈值
   - 去重方式（`DISTINCT` → `GROUP BY` → 窗口）
   - 预聚合 / 物化中间结果
   - 拆分大查询为多步，减少重复扫描
4. **验证**：同一数据、同一时间窗，跑改写前后；对比耗时、扫描量、结果行数与关键聚合值。
5. **回归**：确认结果完全一致（行数 + 校验和 / 抽样比对），再给出上线建议。

## 判定口径

- 语义不变是前提：任何改变结果集的「优化」都必须单独标注为「口径变更」，不能混在性能优化里。
- 只接受可测量的收益：给出前后对比，不给「理论上更快」。
- 一次只改一个变量；同时改三处无法归因。
- 资源换时间要写清楚：物化会占存储、加索引会影响写入。

## 输出格式

```
瓶颈：<定位到计划里的具体算子 + 证据>
改写：<改了什么，逐条>
对比：| 指标 | 改前 | 改后 | 数据来源 |
风险：<结果一致性 / 资源 / 维护成本>
上线建议：<直接上 / 灰度 / 只在大查询用>
```

## 反例

- 没跑过 `EXPLAIN` 就建议「加个索引试试」。
- 为了让数字好看，悄悄改了过滤条件。
- 把「减少一次扫描」和「改口径」混为一谈。
- 优化完不复核结果，只报耗时下降。

## 工具（P1 后可用）

- `sql.explain`：拿计划与扫描量；不可用时要求用户粘贴输出。
- `sql.query`：跑基线/对比查询（只读、有行数上限）。
- `catalog.search`：确认分区字段与统计信息新鲜度。
