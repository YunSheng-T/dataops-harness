# 数据建模评审

## 何时用

- 新建 ODS/DWD/DWS/ADS 层表，或维度表/事实表/宽表
- 修改已有模型的粒度、主键、分区或关键字段
- 有人问「这张表该怎么建 / 放哪层 / 要不要冗余」

不适用：临时中间表（用会话临时表即可）、纯查询优化（用 `sql-optimize`）。

## 先取事实

1. **业务过程**：这张表回答什么业务问题？谁用？怎么用（看板/接口/取数）？
2. **粒度**：一行代表什么？必须能用一句话说清，例如「一个订单一行」「一个用户一天一行」。
3. **维度与度量**：哪些是维度属性、哪些是指标、指标口径是什么。
4. **更新方式**：全量/增量、日更/小时更、是否要历史快照（拉链/快照表）。
5. **规模与生命周期**：日增行数、保留多久、是否需要冷热分层。
6. **下游**：哪些报表/API/任务会消费；是否已有相似模型可复用。

## 流程

1. **先查重**：现有模型里有没有同粒度、同口径的表？能复用就不要新建。
2. **定粒度**：粒度说不清 → 不进入下一步。检查主键在该粒度下是否唯一。
3. **分维度与事实**：维度属性不要堆进事实表；一致性维度（用户/商品/组织）必须复用公共维度。
4. **定分层与命名**：按团队规范（库名/表名前缀/分层后缀）；宽表要写明冗余理由和一致性维护方式。
5. **定分区与生命周期**：分区字段与业务时间对齐；明确保留期与清理策略。
6. **定更新与回刷**：幂等写入方式、历史回刷范围、回刷对下游的影响。
7. **定消费契约**：下游按什么字段、什么口径读；口径变更如何通知。

## 判定口径

- **阻断**：粒度无法一句话描述；主键在粒度下不唯一；与现有模型重复且口径冲突；无分区的大表。
- **需修改**：事实表里塞维度属性；一致性维度各自维护；命名不符合分层规范；无保留期策略。
- **建议**：补字段注释与口径文档；补数据质量规则；补血缘登记。

## 输出格式

```
结论：通过 / 有条件通过 / 驳回
粒度：<一句话>
主键：<字段>，唯一性验证：<SQL 或抽样结果>
分层与命名：<建议名>
分区/生命周期：<字段 + 保留期>
下游契约：<字段清单 + 口径>
风险：<重复建设 / 口径冲突 / 回刷影响>
```

## 反例

- 「先建出来再说」，粒度留到以后补。
- 用「用户 ID + 日期」当粒度，但实际一个用户一天有多条。
- 每个团队各建一张用户维表，口径各不相同。
- 宽表冗余了维度属性，却没写谁负责同步。

## 工具（P1 后可用）

- `catalog.search`：查重、查现有模型与口径。
- `lineage.impact`：评估修改对下游的影响。
- `sql.query`：验证主键唯一性、抽样核对。
