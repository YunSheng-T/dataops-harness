# SQL 评审

## 何时用

- 提交 DDL：建表、改表、删表、加/删索引、改分区策略
- 提交或修改生产 SQL：ETL 任务、报表查询、对外 API 的取数语句
- 有人问「这条 SQL 能不能上 / 会不会锁表 / 要不要改」

不适用：一次性临时取数、只读探索（直接看执行计划即可，不必走完整评审）。

## 先取事实（缺什么就问，不要猜）

1. **引擎与方言**：Hive / Spark SQL / Doris / StarRocks / Trino / MySQL / PostgreSQL …
2. **对象与规模**：库表全名、分区字段、单分区行数、总行数、日增量
3. **变更类型**：新增 / 修改 / 删除 / 重命名 / 改类型 / 改分区
4. **下游**：哪些任务、报表、API 在读这张表或这个字段；没有血缘就明确写「未知」
5. **时间窗**：计划执行时间、可接受停多久、能否回滚

## 流程

1. **方言与语法**：函数是否支持、隐式类型转换、`NULL` 排序、除法精度、字符串截断规则。
2. **扫描与代价**：看 `EXPLAIN`。分区裁剪是否生效？有没有全表扫、笛卡尔积、非必要的 `DISTINCT` 或窗口？
3. **锁与并发**：DDL 是否锁表、引擎是否支持在线变更、是否需要低峰执行；DML 是否会与任务撞车。
4. **幂等与重跑**：`INSERT OVERWRITE` 覆盖范围是否精确？`MERGE` 的匹配键是否唯一？重跑两次结果是否一致？
5. **兼容性**：字段类型收窄、默认值、`NULL` 语义、时区；下游按列位置读还是按列名读。
6. **回滚**：有无备份、能否反做、回滚耗时。

## 判定口径

- **阻断（必须改）**：无分区裁剪的全表扫；会长时间锁表的在线 DDL；不可重跑的非幂等写入；删字段/收窄类型且下游未确认。
- **需修改（可讨论）**：`SELECT *` 落表；隐式类型转换导致索引失效；单分区过大需要重分布。
- **建议**：补注释、统一命名、补监控。

## 输出格式

```
结论：通过 / 有条件通过 / 驳回
阻断项：<逐条，带证据：计划片段 / 行数 / 下游清单>
风险项：<等级 + 触发条件 + 缓解办法>
必改清单：<可直接照做的修改>
验证 SQL：<上线前跑什么、预期结果是什么>
回滚方案：<一句话，包含回滚窗口>
```

## 反例

- 只看语法不看执行计划，把「应该没问题」当结论。
- 用「表不大」当理由，却拿不出行数。
- 下游影响写「应该没有」——没有血缘证据就写「未知，需人工确认」。
- 把建议项写成阻断项，评审会失去可信度。

## 工具（P1 后可用）

- `sql.explain`：执行计划与扫描量。不可用时让用户粘贴 `EXPLAIN` 输出。
- `lineage.impact`：下游清单。不可用时要求提供血缘截图或人工确认。
- `catalog.search`：确认表/字段存在性、类型、分区字段。
