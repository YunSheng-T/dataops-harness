# 数据服务契约评审（SQL → API / 报表）

## 何时用

- 把一条 SQL 发布成对外 API（内部服务间调用或开放接口）
- 配置/修改报表、看板、导出任务
- 修改已上线数据服务的字段、口径、过滤条件或权限
- 有人问「这个接口能不能改 / 加个字段会不会影响调用方」

不适用：纯内部临时取数；还没确定口径的探索性分析。

## 先取事实

1. **消费方**：谁调用、调用频率、是否有 SLA
2. **契约**：字段名、类型、含义、空值语义、排序、分页
3. **口径**：指标定义、时间范围、时区、去重规则、数据延迟
4. **权限**：行级/列级权限怎么控制，调用方身份怎么传
5. **性能**：预期 QPS、单次扫描量、缓存策略
6. **变更类型**：加字段 / 改类型 / 改口径 / 改权限 / 下线

## 流程

1. **契约对齐**：字段逐个确认「名、型、义、空」。同名不同义是最常见的坑。
2. **口径固化**：把指标定义写成一句话 + 一段可执行 SQL，二者必须一致。
3. **性能评估**：单次查询扫描量与延迟是否满足 QPS；不做全表扫、不做无界分页。
4. **权限设计**：调用方身份从哪来、行级过滤在哪一层执行、越权返回什么。
5. **兼容性判断**：
   - 加字段：通常兼容（确认调用方不是严格 schema 校验）
   - 改类型/改语义：**破坏性**，必须新版本或新字段
   - 下线字段：先标记 deprecated，观察调用量归零再删
6. **监控与回滚**：错误率、延迟、空结果率；回滚到上一版 SQL/配置的路径。

## 判定口径

- 破坏性变更必须版本化（新接口/新字段/新报表），不能原地改。
- 口径变更即使字段名不变，也是破坏性变更——必须通知并标注生效时间。
- API 不允许全表扫描或无界导出；必须有行数/时间范围上限。
- 报表必须能追溯到具体 SQL 版本与数据时间，否则无法复核。

## 输出格式

```
服务：<名称>  变更类型：<加字段/改口径/下线…>
契约 diff：
| 字段 | 变更前 | 变更后 | 兼容性 |
口径：<一句话定义 + SQL 版本>
性能：<扫描量 / 延迟 / 缓存>
权限：<身份来源 + 过滤层>
上线检查单：<逐项勾选>
回滚：<版本回退方式 + 数据影响>
```

## 反例

- 字段名不变但口径变了，当成「小改动」直接发。
- API 直接 `SELECT *` 全表导出。
- 权限靠调用方传参声明，服务端不复核。
- 报表数字对不上时，找不到当时跑的 SQL。

## 工具（P1 后可用）

- `catalog.search`：查资产与调用方。
- `sql.explain`：评估发布查询的代价。
- `lineage.impact`：查该服务/报表的下游。
- `service.contract diff`（P2）：对比线上契约与待发布版本。
