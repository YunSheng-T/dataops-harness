# 血缘影响面评估

## 何时用

- 改字段类型/含义、重命名、删除字段
- 下线表、迁移库、切换数据源
- 修改指标口径（哪怕字段名不变）
- 有人问「这个改动会影响谁」

不适用：新增字段/新增表（影响面通常为空，但建议仍查一次下游）。

## 先取事实

1. **对象**：库.表.字段，变更的精确范围（表级还是字段级）
2. **变更类型**：新增 / 类型变更 / 语义变更 / 重命名 / 下线
3. **生效时间**：什么时候切、是否有并行期
4. **已知消费方**：报表、API、任务、外部系统、临时取数
5. **血缘质量**：有没有字段级血缘；没有就明确降级为人工盘点

## 流程

1. **查直接下游**：视图、任务、API、报表、导出。字段级优先，表级兜底。
2. **递归到终端消费方**：任务的下游任务、API 的调用方、报表的使用者。
3. **分类**：
   - **强依赖**：字段被直接读取或参与计算 → 必须迁移后才能改
   - **弱依赖**：仅透传、仅展示、或已无人使用 → 可并行/可下线
   - **未知**：血缘缺失 → 人工确认，不能默认安全
4. **定策略**：加字段过渡（双写/双读）→ 切换 → 观察 → 删除旧字段；每一步给时间窗。
5. **通知与验证**：受影响方确认；切换后抽查下游数据一致性。

## 判定口径

- 字段级优先于表级；表级影响面只能用来「兜底找人」，不能用来判断兼容性。
- 读依赖和写依赖分开列：写这张表的任务也要改，否则会被新 schema 打断。
- 没有血缘证据的「应该没人用」= 未知，不是安全。
- 下线必须有观察窗口，窗口内保留回滚能力。

## 输出格式

```
变更：<对象 + 类型 + 生效时间>
影响清单：
| 消费方 | 类型（报表/API/任务） | 依赖级别 | 依赖字段 | 处置 | 负责人 |
风险：<强依赖未迁移 / 血缘缺失 / 外部消费方>
迁移步骤：<1..n，含验证点>
回滚：<怎么退、退多久>
```

## 反例

- 只看表级血缘就判断「没人读这个字段」。
- 漏掉写这张表的任务（改 schema 后写入失败）。
- 迁移和删除放在同一天。
- 通知了任务负责人，却没通知报表和 API 的调用方。

## 工具（P1 后可用）

- `lineage.impact`：字段级/表级下游。不可用时要求人工提供血缘导出。
- `catalog.search`：确认对象与字段是否存在、被哪些资产引用。
- `sql.query`：切换后做一致性抽查。
