03 · Deliverable Flow

内容从技能出来，卡片从 presenter 进去

Agent 负责判断与正文；presenter 只做 transport + validation；client 只按 kind 分发。
Agent + 技能

dataops-workflow + dataops-deliverable-templates 产出需求/设计/方案/开发/复盘正文。

→
Deliverable JSON

{kind, stage, deliverable, status, payload, source, asOf, gaps}，落盘到 workitem/deliverables。

→
dataops_shared_present_deliverable

校验 kind/stage/path/payload；透传 payload；不生成、不审批、不写工作项。

→
DeliverableRenderer

按 kind 分发到现有 8 类卡片；stage brief 继续按 kind 更新。

Agent 之后还要做的事

调用 dataops_shared_update_workitem 记录 stage、deliverables、gaps、next；发布仍调 release 触发 DSH approval。

为什么不让 presenter 直接写工作项

展示与状态是两件事。presenter 只做无副作用展示；工作项写入有独立 schema/原子性/审计要求。

04 · Contracts

Deliverable / Presenter / 校验

输出保持 payload 平铺，现有 parseModel(block, kind) 不改；减少卡片回归面。
// deliverable（Agent/技能产出） { kind: "tech_plan", stage: "scheme", deliverable: "deliverables/tech-plan.yaml", status: "draft", payload: { tasks: [...], estimate: "2 人日", risks: [...] }, source: "agent", asOf: "2026-10-26T18:00:00+08:00", gaps: [] }
// presenter 输出（卡片直接消费） { ...payload, kind: "tech_plan", stage: "scheme", deliverable: "deliverables/tech-plan.yaml", status: "draft", source: "agent", asOf: "...", gaps: [], presented: true }
只校验结构

kind 允许列表、kind/stage 映射、安全相对路径、payload 是 object、status 枚举、256 KB 上限。缺字段返回错误，不猜测。

绝不越界

不生成/改写 payload；不读写 workitem；不调 DSH approval；不回调 Agent；不访问外部平台。

05 · Card Dispatcher

一个 presenter，复用 8 张卡

旧卡片组件不重写；新增一个 dispatcher，把 kind 映射到已有组件。
DeliverableRenderer 是什么：它不是一张新的业务卡，也不是 deliverable 本身，而是一个 toolview 分发器：收到一份带 kind 的 deliverable，按 kind 交给现有卡片。叫 Deliverable 是因为输入是工作项里可落盘、可 diff、可审计的交付物，不是工具临时返回或聊天文本。

06 · Workitem & Logs

工作项和排障也收成原子能力

P2 用文件适配；P3 服务化。审批仍是 DSH approval，工作项只做记录。
dataops_shared_read_workitem

按 id 读取 item.yaml 的结构化字段；不返回原始大文件；找不到时返回列表/明确错误。

dataops_shared_update_workitem

只允许更新 stage/substage/status/stages/next/gaps/approvals/deliverables/evidence；schema + 原子写 + 路径校验；非法 stage 拒绝。

dataops_shared_read_logs

只读时间线、错误码、上下游任务、最近运行；不下根因结论。根因由 pipeline-debug 技能完成。

incident 卡

pipeline-debug 产 incident deliverable → presenter → IncidentCard；incident_triage 退出活动工具面。

安全：update_workitem 的 approvals 只记录，不是权限；release 工具仍调用 DSH 原生 approval，只允许 `allowed-once`。

08 · Acceptance

P2 的完成标准

P2.0 只定设计；下面这些是 P2.4 的验收，不是今天已经完成。
12 个活动工具，不再有内容生成 tool
8 类 deliverable 经 presenter 渲染，视觉与 P1 一致
工作项由 read/update 工具维护，非法变更 fail closed
release 仍只 allowed-once 才执行
P1.4 query / full-allow / full-reject 继续 PASS
最终回答不暴露工具名
Presenter 变成内容生成只校验/透传；禁止改 payload；专用测试
DeliverableRenderer 回归8 类 golden payload + 现有卡 DOM 断言
技能正文质量下降先 requirement/design pilot，与旧工具逐字段对比
旧工具消失导致演示断P2.1–P2.3 并存；P2.4 才退出注册
角色工具面未隔离P2 静态 12；P3 做 dynamic tool policy
