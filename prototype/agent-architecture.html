01 · Entry & Journey

从一个需求到 6/6

阶段模型不变；变的是谁拥有阶段、谁记状态、谁决定下一步。橙色是阶段 artifact，青色是共享事实/能力。

需求

Lead · 接单

Stage 05

CICD

Lead · 门禁

扫描 → 编译 → 测试 → 发布；发布前必须 approval。
子步骤：4 步 · 硬门禁
Stage 06

复盘

Lead · 沉淀
postmortemcicd-report

退出：工作项完成
旧：工具目录式入口（只适合验收）

dataops_requirement_extract_spec → dataops_design_compose_model → … 用户要报 12 个工具名，阶段靠 prompt 记。

新：需求式入口

用户说业务目标；Lead 建工作项、判断阶段、调内部能力，发布前停。工具名只出现在实现和测试里。

关键变化：“阶段”仍然存在，但不再等于一个 tool。阶段由工作项状态机拥有；内容由Agent + 技能产出；卡片由 artifact 渲染。
02 · Runtime Topology

谁在用户和外部系统之间

用户面只表达目标；Agent 负责路由；工作项负责硬状态；技能负责阶段知识；工具负责原子能力。
L0用户面

自然语言 · 工作项 · 阶段卡 · 审批

用户只说目标、范围、验收；看阶段卡和 artifact；发布前审批。没有工具名、没有 JSON。

WorkItem + Stage State Machine 硬约束

L3能力

原子工具 + 阶段技能

工具：只读事实、CICD 动作、工作项、deliverable renderer。技能：需求/设计/方案/开发/复盘的方法与模板。内容生成不放在 tool。

L4外部

DataMap · 查询 · 调度 · CICD · 审批

默认只读；写平台走现有审批/发布系统。凭据只经 credentials，不进 prompt/日志。

硬骨架（可验证）

preset + 工作项状态机 + 发布 approval。决定阶段是否允许推进，不依赖模型是否“记得”。

P1 开始
软知识（可替换）

阶段技能、模板、判定口径。可以随时改，不需要改工具或 UI；也不能替代状态机。

P0 已有
为什么不是 Agent Team

单 Lead 先跑通；只有评审/血缘/排障需要上下文隔离时才派子代理。线性需求不需要多 Agent 协调。

为什么不是 workflow

workflow 适合批量 fan-out；单个需求是线性、有人审、有状态的流程，应该用工作项状态机。

05 · Delivery Sequence

发布前必须停

状态机和工具双重校验 approval；prompt 不是权限边界。排障走旁路，不污染主链。
1用户说业务目标，不说工具名；可附工单/表/验收。
2Lead建立/恢复 workitem；提取目标、范围、验收、owner；缺关键项只问一个。
3Lead需求 → 设计 → 方案；按需读事实、产 artifact、调 presenter 出卡。
4Lead开发 → 扫描 → 编译 → 测试；状态机记录每步产物和 gaps。
!Gate发布前停：变更单、窗口、审批人、回滚展示给用户；写 approvals[gate=release]=pending，不调 release。
5用户确认/驳回；确认后 approval=approved，Lead 才能调 release（带 token）。
6Lead复盘：目标 vs 实际、行动项 owner/期限、知识回写；工作项进入 done。

07 · Decisions

需要拍板的三件事

架构先定，再落 P1；以下建议不阻塞设计评审。

WorkItem 先文件还是先服务？

P1 用 `workitems/` 文件协议，先解决 Agent 连续性与可 diff；P2 再服务化，接口先定。

建议：P1 文件

单 Lead 还是 Agent Team？

单 Lead 先跑通 6 阶段；评审/血缘/排障需要上下文隔离时再加子代理，不先上多 Agent。

建议：单 Lead

内容工具何时收？

P1 保留旧 mock 工具做兼容/回归；P2 用 presenter 迁移内容，写 ADR，再删旧工具。

建议：P2 再收
